runserver vs gunicorn

Same one-core container, same test. Swapping Django's dev server for gunicorn with 4 workers took the API from collapsing under load to degrading gracefully: 2.7× the throughput, zero failed requests, and half the memory.

runserver's 512.0 MiB is the container limit — it peaked at 99.99% of the cap. k6 request errors: 1,073 request timeout · 337 dial timeout · 51 connection reset.

Reading it

runserver collapsed; gunicorn degraded

runserver settled at ~22 req/s with 42% of requests failing — timeouts, dial timeouts, connection resets. gunicorn sustained ~62 req/s with zero failures; every request was answered, just slowly.

stress.js uses an open model, so a slow server doesn't get a lighter load — it gets a growing queue. runserver dropped that queue on the floor; gunicorn held it.

The connection stall is gone

http_req_connecting p95 went from 5.11 s to 0.45 ms (max 19.7 s → 8 ms). runserver has one accept() loop and a small listen backlog, so new TCP connections waited through the kernel's SYN-retransmit backoff — roughly 1 s, 3 s, 7 s, 19 s, the exact outliers seen.

gunicorn's 4 workers accept in parallel behind a larger backlog, so connection setup stays sub-millisecond even while the app is saturated.

Server-side latency: 75 s → 97 ms

Under runserver, Django's own latency histogram maxed out at 75 s. Under gunicorn each request is served in ~100 ms.

With runserver, requests queued inside the Python process — GIL plus a single accept loop. With gunicorn the multi-second http_req_duration is almost entirely time in the OS accept queue waiting for one of the 4 workers to free up (http_req_waiting ≈ http_req_duration, http_req_connecting negligible). That's honest back-pressure, not the app choking.

runserver sat on the memory limit

manage.py runserver is threaded — roughly one thread per in-flight connection. At 500 VUs that's ~500 thread stacks plus buffers, and the working set pinned the container's 512 MiB limit (99.99% of it — one bad moment from an OOM kill).

gunicorn's 4 sync workers have a bounded footprint no matter how deep the queue: 220 MiB, flat.

Both are CPU-bound at the one-core cap

CPU averaged ~0.75 cores with ~60% CFS throttling in both runs — the cpus: "1.0" limit is the ceiling, and the server choice doesn't move it. gunicorn's wins are the concurrency model, failure behaviour, connection handling and memory — not raw compute.

Neither reached 400 req/s

20k–33k dropped iterations in both runs. GET /api/clients/ is CPU-bound — serialization, pagination — and the container has one core. Serving 400 req/s means raising the CPU limit; adding workers alone won't help on a single core.
