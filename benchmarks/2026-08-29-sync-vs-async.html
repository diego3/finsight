sync vs async

Same 4-core API container, same test, only the worker model changed. Running the sync Django app under ASGI + uvicorn workers made it slower and less reliable: −7% throughput, 31% of requests failing, and per-request latency ~50× worse. For a sync codebase, WSGI wins.

Both runs crossed stress.js's thresholds (k6 exit 99) — expected. Runs ~50 s apart, 16-core host. The API container's throughput peak (Django, 220 vs 188 req/s) is higher than k6's sustained rate because it counts the brief moments before the accept queue built up.

Reading it

Async lost on every axis that matters

Throughput dropped 7%, a third of requests returned HTTP 500, and server-side p95 went from 76 ms to 3.76 s. There is no column in the table where ASGI came out ahead on this workload — only http_req_connecting, which was already a non-issue.

A sync view under ASGI still runs in a thread pool

Every FinSight view is def, not async def, and the ORM calls are sync. Under ASGI, Django wraps each one in sync_to_async and runs it in a thread executor. So a request now pays for the asyncio event loop, the loop→thread handoff, and asgiref's context machinery on top of the identical sync work.

It shows in the CPU: async pinned the container at 4.0 / 4 cores with up to 100% throttling; sync did the same work coasting at 1.4 cores with no throttling.

Async exhausted the Postgres connection pool

Peak backends: 8 under sync, 100 under async — and max_connections is 100.

gunicorn's process model is a natural limiter: 9 sync workers handle at most 9 requests at once, so at most ~9 DB connections. uvicorn workers each run many requests concurrently through their thread pool, and with CONN_MAX_AGE=0 every in-flight request opens its own connection. It walked straight into the ceiling, and Postgres answered the overflow with FATAL: sorry, too many clients already — the 10,254 HTTP 500s.

The database is the real ceiling for both

sync bottlenecks on DB CPU: 844 transactions/s is mostly connection churn (a connect + auth + the query + disconnect per request), and the db container sat pinned at 2 / 2 cores. async bottlenecks on DB connection count. Same root cause — CONN_MAX_AGE=0 and no connection pooler.

Async did make TCP accept instant

http_req_connecting p95 went from 362 µs to 0. uvicorn's asyncio accept loop never blocks. It is the one thing ASGI is unambiguously good at here, and at this scale it changes nothing — the latency is all accept-queue wait and thread-pool contention behind it.

Next

  • Add CONN_MAX_AGE (or pgbouncer) and re-run both — the interesting comparison is sync vs async with pooling, where the connection ceiling no longer decides it.
  • Raise DB_CPUS to 4 and re-run sync: is it still DB-CPU-bound, or does the app tier become the limit?
  • If staying sync (the call for this codebase): raise GUNICORN_WORKERS and tune --backlog, re-measure.
  • Async is only worth revisiting once views are genuinely async def with an async ORM or async external calls — not applicable today.
